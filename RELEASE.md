# Reproducible build & release

Anyone can rebuild the canister from a tagged commit and check that the bytes running on
mainnet are the bytes that commit produces. This is the procedure for both sides.

## What is pinned

Every tool that shapes the module bytes is pinned by the committed tree:

| What | Where pinned |
|------|--------------|
| `moc` 1.16.0 | `mops.toml [toolchain]` |
| Motoko dependencies (`core`, `sha2`, `ic`) | `mops.lock` |
| `@dfinity/motoko@v5.1.0` / `@dfinity/static-site@v0.3.3` recipes | `icp.yaml` (icp-cli rejects unpinned recipes) |
| `icp` 1.5.0, `ic-wasm` 0.11.1, `mops` 3.2.2, Node 24.21.0 | `ghcr.io/dfinity/icp-dev-env-motoko:v2.2.1`, pinned **by digest** in `Dockerfile.release` |
| The pinned crypto submodule | the gitlink in the ref itself; `reproducible-build.sh` reads it with `git ls-tree <ref>`, never from the working tree |
| Candid interface | `src/backend/dist/backend.did`, committed; the recipe embeds this file as the `candid:service` metadata |

The backend recipe runs `ic-wasm` shrink and embeds metadata (`candid:service` public;
`candid:args`, `motoko:stable-types`, `enhanced-orthogonal-persistence`, `moc:version`
private). The module is not gzip-compressed, so `sha256sum` of the wasm and
`icp canister status` are directly comparable.

⚠️ **Bumping the dev-env image can move every module hash** (`ic-wasm` shrinks the module
and embeds its metadata). A bump is a release of its own with its own published hashes,
never a passenger on unrelated work. Take the **index** digest from
`docker buildx imagetools inspect ghcr.io/dfinity/icp-dev-env-motoko:vX.Y.Z`, not a
per-platform one, so `--platform` still selects the right child.

`scripts/release.sh` and `scripts/reproducible-build.sh` write `backend.wasm`,
`frontend.wasm`, `backend.did` and `MODULE-HASHES.txt` into `release/` from
`git archive <ref>`, so local changes cannot reach a hash. `frontend.wasm` is the pinned
recipe's pre-built canister, identical for every project using it, and proves nothing
about the page.

## Cutting a release

```bash
# 1. CHANGELOG.md: rename "Unreleased" to the version, commit it
git tag -a vX.Y.Z -m "vX.Y.Z" && git push origin vX.Y.Z

scripts/release.sh vX.Y.Z                                        # 2. build, print hashes

# 3. publish. release/NOTES.md is generated by step 2: the changelog section, the
#    hashes as a table and verbatim for `shasum -c`, the build architecture, and how
#    to reproduce them.
gh release create vX.Y.Z --prerelease --verify-tag -t vX.Y.Z \
  --notes-file release/NOTES.md

scripts/release.sh vX.Y.Z --install -e ic --identity <operator>  # 4. install + gate

icp deploy frontend -e ic && scripts/check-frontend-hash.py -e ic     # 5. frontend

# 6. update the Status line in docs/VERIFY.md — one sentence, naming this version
```

- **Step 1 comes first because the check reads the tagged tree.** `release.sh` refuses a
  version whose `CHANGELOG.md` has no `## X.Y.Z` section, and looks inside the ref, so
  the entry cannot be backfilled. Building `HEAD` to inspect hashes needs no entry.
- **Step 2 builds from the tag**, the backend from `git archive` in the container and
  the frontend from a worktree at the tag, never from your checkout. One changed HTML
  comment on `main` is enough to change the state hash.
- **Step 4 rebuilds in the container, installs that artifact with
  `icp canister install --wasm`, then reads the module hash back from the canister and
  fails if it differs.** The gate is inside the step on purpose: a separate verification
  instruction gets skipped, and a skipped verification looks like a passing one.
- ⚠️ **Never `icp deploy` the backend.** It rebuilds on the host, so a container build
  followed by `icp deploy` publishes one module and installs another.
- ⚠️ **Do not attach the wasm to the release.** A downloadable module invites trusting
  bytes instead of rebuilding them. Publish the hashes.
- **The frontend is checked by its state hash, not its module hash.** The
  `@dfinity/static-site` recipe installs a pre-built certified-assets wasm; the content
  lives in canister state. `check-frontend-hash.py` compares the canister's `state_hash`
  against one computed from `src/frontend/dist` by the verifier that release ships. The
  hash covers every asset's bytes in every encoding, its `content_type` and response
  headers, and the redirect rules in match order, so a drifted CSP fails it.
- **Step 6 is the one thing no script can check.** `docs/VERIFY.md` tells a visitor what
  is published to compare against; it is one line so updating it is cheap and
  forgetting it is obvious.

## Verifying a release (anyone)

No identity, no permissions.

```bash
git clone <repo> && cd <repo> && git checkout vX.Y.Z

scripts/reproducible-build.sh vX.Y.Z          # rebuild the backend in the container
icp canister status <backend-id> -n ic -p     # read the deployed module hash

npm --prefix src/frontend ci && npm --prefix src/frontend run build
scripts/check-frontend-hash.py -e ic          # compare the served state hash to that build
```

The frontend check builds its verifier from `dfinity/certified-assets` at the tag
`icp.yaml` pins, so it needs a Rust toolchain on the first run and caches the binary
under `.cache/`. It refuses to compare unless the canister's own `version()` matches
that pin: the state hash is frozen per certified-assets release, so bumping
`@dfinity/static-site` invalidates every hash published before it.

`-n` takes an id, `-e` a name: `icp` refuses a network flag when the canister is named
rather than addressed by principal.

`release/MODULE-HASHES.txt`, the hash in the release notes and the canister's
`Module hash` must all agree, and so must the `# build arch:` line. The module hash is
also on the public dashboard (`dashboard.internetcomputer.org/canister/<id>`).

Beyond the two hashes, every HTTP response carries `IC-Certificate` and
`IC-CertificateExpression` over the asset tree and the gateway rejects a response whose
certificate does not verify; there is no uncertified raw mode to turn off.

## Caveats

- ⚠️ **`backend.wasm` depends on the platform it is built on.** The same commit yields
  different hashes on `darwin/arm64` native, `linux/arm64` container and `linux/amd64`
  container. `reproducible-build.sh` pins `--platform linux/amd64`
  (`RELEASE_PLATFORM=` overrides) and `MODULE-HASHES.txt` records the architecture.
- Recipe tags (`@dfinity/motoko@v5.1.0`) are fetched from `dfinity/icp-cli-recipes` by
  git tag, which is not content-addressed. A moved tag changes the hash, so it cannot go
  unnoticed, but it would break reproducibility of old tags. Accepted for v1.
- `MODULE-HASHES.txt` in release notes is trust-on-first-publish; the reproducible build
  exists so nobody has to take it on faith.
